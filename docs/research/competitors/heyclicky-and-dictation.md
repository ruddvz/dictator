# Build Dictator Around Proven Dictation Workflows

HeyClicky's latest Mac release, 1.1.5 from November 16, adds an 18-language interface, new plans and usage resets, a camera-island notch, smoother live replies, retained drawings, and better agent recovery. Its wider assistant can inspect the screen and act on the computer. The most relevant dictation ideas are narrower: fast held-key speech, hands-free mode, language detection, optional correction learning, and dependable insertion across apps. A curated scan of open-source competitors finds strong examples in per-app workflows, local model choice, correction tools, file transcription, meeting support, and offline operation. Dictator already covers many of those areas, but its own audit still flags live insertion acceptance, streaming into the destination field, and automatic language choice as gaps. This review implements a narrow, user-approved local correction-learning offer; reliable insertion remains the priority. Screen capture and computer-use agents are a separate product and consent decision.

## HeyClicky's newest release polishes the assistant around dictation

The latest Mac changelog entry found is **version 1.1.5, dated November 16, 2026**. It localizes the interface into 18 languages, adds plan and billing controls plus paid usage resets, reshapes the Mac notch into a camera-island layout on newer MacBook Pros, animates the transition from typing dots into line-by-line replies, scrolls the chat as it grows, keeps drawings in conversation history, and improves agent outage retries and user handoffs. Version 1.1.3 also added answer-style memory, screen re-checks during walkthroughs, approved file uploads, repeatable jobs, stop/steer controls, and captions that continue after chat closes. ([HeyClicky changelog](https://www.heyclicky.com/changelog))

The core dictation workflow is more directly comparable: hold a shortcut to stream speech into other apps, double-tap for hands-free dictation, automatically detect more than 50 spoken languages, and learn a vocabulary entry when a user edits a recent transcript. HeyClicky also offers explicit screen-aware drafting: the user asks for a contextual reply, then the app captures the screen and drafts from it. Its wider Mac product includes voice or typed chat, screen explanations, visual pointers, connected services, and task agents. ([HeyClicky changelog](https://www.heyclicky.com/changelog), [Mac product page](https://www.heyclicky.com/for-mac))

Those capabilities carry a broader data boundary than Dictator's local dictation path. HeyClicky requests microphone, screen-recording, and accessibility permissions; its terms say keyboard and mouse actions require user approval. Its privacy policy says screenshots are not stored on HeyClicky's servers, but providers may retain them briefly for processing or safety, while text summaries and task context can persist. HeyClicky also says it disabled proactive agents and removed related local activity tracking after privacy concerns. These are useful product lessons about visible activation and user control, not evidence that screen monitoring or agents belong in Dictator by default. ([HeyClicky terms](https://www.heyclicky.com/terms), [privacy policy](https://www.heyclicky.com/privacy-policy), [changelog](https://www.heyclicky.com/changelog))

## Open-source competitors win in different parts of the workflow

## Dictator has breadth, but core insertion is still the gate

Dictator already offers configurable hold or toggle dictation, Apple on-device streaming recognition, optional local Parakeet transcription, review/edit/copy/guarded insert, writing modes, app profiles, snippets, correction rules, selected-text editing, single-file transcription with subtitle export, and meeting capture with local notes. It also has opt-in nearby text hints that read only a bounded area around the cursor in supported non-password fields and discard the source text. ([Dictator README](https://github.com/ruddvz/dictator/blob/main/README.md), [text insertion source](https://github.com/ruddvz/dictator/blob/main/Dictator/Services/TextInsertionService.swift))

The differences matter: Dictator's existing vocabulary and correction rules are user-managed; it does **not** currently implement HeyClicky's edit-a-recent-transcript-to-learn-a-word loop. Live language selection is manual, although file transcription has auto-detect. Dictator inserts completed phrases rather than incrementally revising text inside the target field. Its meeting flow lacks speaker identification, and file transcription handles one recording at a time. Most critically, the project record still says live insertion into a real destination app and permission acceptance are not verified end to end. ([personalization view](https://github.com/ruddvz/dictator/blob/main/Dictator/Views/Hub/PersonalizationView.swift), [file transcription view](https://github.com/ruddvz/dictator/blob/main/Dictator/Views/Hub/FileTranscriptionView.swift), [progress record](https://github.com/ruddvz/dictator/blob/main/PROGRESS.md))

The feature comparison cannot establish which app transcribes more accurately or types more reliably. Competitor repositories document feature claims and release activity, but this review did not run comparable speech tests, profile insertion success rates, or benchmark scroll/latency. Dictator should use those as test questions, not marketing claims, until it has its own measured results.

## A safe roadmap starts with reliability and reversible learning

**First, close the insertion gap.** Make permissions, focused-target detection, delivery method, clipboard fallback, and recovery state observable; confirm that a single dictated phrase lands once in representative native, browser, and Electron fields. Keep the existing target validation and explicit recovery behavior. The app's progress record still marks the live permission and Codex insertion acceptance as open, so new capabilities should not be presented as finished until that path passes. ([text insertion source](https://github.com/ruddvz/dictator/blob/main/Dictator/Services/TextInsertionService.swift), [progress record](https://github.com/ruddvz/dictator/blob/main/PROGRESS.md))

**Implemented in this review: user-controlled correction learning.** After a reviewed transcript changes by exactly one distinctive word, Dictator previews the recognized and corrected words. The user can add only the corrected word to the on-device vocabulary, dismiss the offer, or undo a saved word. The heuristic rejects common-word changes, multiple changes, and token-count changes; it never stores the transcript or learns without the user's action. Unit tests cover those guardrails. This is narrower than HeyClicky's time-windowed automatic dictionary learning and intentionally requires explicit approval.

**Next, close the insertion gap.** The progress record still marks live permission acceptance and exact-once insertion into a real destination app as open. Treat this as the priority before streaming into the target field, automatic language selection, queued file transcription, or speaker labeling. ([Text insertion source](https://github.com/ruddvz/dictator/blob/main/Dictator/Services/TextInsertionService.swift), [progress record](https://github.com/ruddvz/dictator/blob/main/PROGRESS.md))

**Then improve live feedback and recovery.** Consider an optional streaming-into-field mode only after target tracking can safely replace interim text without duplication, preserve the caret, and undo the inserted segment. Separately explore automatic language selection with confidence and fallback, retention across microphone/call interruptions, safe clipboard restoration, and correct spacing/newlines for CJK text and terminals. A multi-file queue and editable speaker labels can follow the insertion work. These ideas map to documented competitor gaps, but each needs its own acceptance criteria before release.

Screen-aware drafting, connected services, persistent cloud memory, visual click/draw controls, routines, and autonomous agents should remain separate proposals. If pursued later, they need a distinct permission flow, per-request screen capture, clear cloud routing and retention, action confirmation, stop/recovery controls, and a reviewable safety boundary. HeyClicky's own product history—especially disabling proactive agents after privacy concerns—shows why these features should not be bundled invisibly into dictation. ([HeyClicky changelog](https://www.heyclicky.com/changelog), [privacy policy](https://www.heyclicky.com/privacy-policy))

## Conclusion

Dictator does not need to match every surface feature in HeyClicky or the broadest open-source apps to compete. Its strongest position is a reliable, local-first dictation path with strong per-app writing, recoverable insertion, and user-owned vocabulary. The next implementation should be small enough to validate on the user's Mac and meaningful enough to improve the failure they have repeatedly encountered; broader assistants and screen agents can wait until Dictator's basic “speak, insert once, recover cleanly” promise is proven.
