# Make HushKey Win Through Reliable Workflows

**Research date:** 1 November 2026.

The strongest products in this comparison turn speech into usable writing through a short, recoverable loop: start capture, show what is happening, produce text that respects the user's intent, and insert it into the right place. HushKey already implements much of the feature breadth—local dictation, modes, vocabulary and snippets, transforms, guarded insertion, history, file transcription, and meeting notes—so rebuilding those areas or adding a long list of engines is not the best next move. The largest gap is proving the existing paths work reliably on the user's Mac, then improving their visibility and recovery. The most valuable net-new capability is a carefully guarded voice-edit mode for selected text, followed by clearer recording-state feedback and configurable app profiles. Competitor claims establish useful product patterns, not comparative accuracy or speed: none of the supplied roundups is a shared lab benchmark. HushKey should adopt the patterns in its own interface and code, preserve its local-first promise, and gate expansion on end-to-end acceptance.

The primary project repositories and help centers support the feature descriptions above; the roundups add a useful taxonomy but do not establish which app is best. OpenWhispr's comparison page is written by a competitor and should be treated as positioning, not an impartial test ([OpenWhispr comparison](https://openwhispr.com/compare/wisprflow)). The OpenTypeless website's app-count, language-count, and support claims are likewise product claims; SpeakType's model-size and language figures are maintainer documentation, not independent validation ([OpenTypeless](https://www.opentypeless.com/en), [SpeakType](https://github.com/karansinghgit/speaktype)).

The Reddit post points to **SpeakType**, a project separate from OpenTypeless. Its README and releases describe offline models, correction rules, history/replay, file transcription, and a recording-state interface. Two commenters reported a microphone indicator that stayed on or model-loading delays, but these isolated posts do not prove current defects. They do support a general acceptance check: every stop, cancel, error, and permission-denied path should visibly settle and release the microphone ([Reddit thread](https://www.reddit.com/r/LocalLLM/comments/1s03cte/i_made_a_free_opensource_wisprflow_alternative/), [SpeakType releases](https://github.com/karansinghgit/speaktype/releases)).

## HushKey already covers breadth; reliability and discoverability remain

HushKey's product plan and implementation notes describe an unusually broad local Mac foundation: on-device voice/whisper dictation, Natural/Message/Email/Code/Automatic modes, global shortcuts, custom terms and snippets, spoken corrections with raw restore, optional bounded nearby-text hints, guarded insertion and undo, local history, review-first transforms, Apple Speech or optional WhisperKit file transcription with TXT/SRT/VTT export, and explicit microphone/system-audio meeting capture with local summaries and action items. Silent Lab remains a separate research workflow. The [product plan](PRODUCT_PLAN.md) and [progress log](../PROGRESS.md) record these as implementation coverage, not proof that every hardware and permission path has passed manual acceptance.

| HushKey area | Current coverage in project notes | Gap that matters next |
|---|---|---|
| Capture and insertion | Hold/toggle and start/stop controls, editable transcript, copy, guarded one-time insertion and undo | Complete live microphone/Speech permission, global shortcut, focus, TextEdit plus second-app insertion and no-duplicate recovery checks |
| Cleanup and personalization | Five writing modes, spoken correction/raw restore, terms/snippets, local correction rules, optional nearby hints, local transforms | Ensure feedback and errors are obvious; add dictionary import/export and validate correction behavior in live dictation |

| Local processing | Apple Speech zero-download route; optional downloaded WhisperKit; local Foundation Model transforms when supported | Make model size, download progress, warm-up, offline state, and failure recovery legible; compare models on target hardware before recommending one |
| History and recovery | Local dictation history, raw/processed restore, searchable file jobs, meeting-note search/edit/export/delete | Ensure paste-again is deliberate and focus-checked; manual acceptance is still open; avoid retaining audio by default |

The immediate gap is not a missing competitor checklist. Project notes explicitly leave manual acceptance open for voice and whisper capture, shortcuts, insertion/undo, file engines, and the three meeting audio sources. Passing unit tests and producing a signed app do not verify live microphone behavior, Accessibility focus, insertion into another application, downloaded model behavior, or system audio ([testing protocol](TESTING_PROTOCOL.md), [progress log](../PROGRESS.md)).

## Implement recovery and selection editing before adding more modes

These rankings are HushKey-specific product judgments, not measured market scores. Effort assumes the current architecture can be extended and may change after manual acceptance.

| Rank | Improvement | Impact / effort | Why it should come here |
|---:|---|---|---|
| 1 | **Manual end-to-end acceptance and fix the failures found** | Very high / medium | Every other workflow depends on capture, shortcut, focus, and safe insertion working. Preserve a checklist for permission denial, stop/cancel/error release, no transcript loss, duplicate prevention, undo, and second-app focus. |
| 2 | **Recording status capsule and explicit recovery** | High / medium | Show idle, recording, processing, ready, and error; include a mic-level indicator only while capture is active, plus cancel/retry and a focus-checked “Paste again.” Keep the draft on failure and never silently paste twice. | 4 | **Extend app profiles and personalization portability** | High / medium | HushKey now supports local app profiles for writing mode and vocabulary, matched by bundle identifier. Do not prioritize a generic voice assistant, arbitrary voice macros that execute actions, a plugin marketplace, or a larger provider catalog. They increase mode confusion, credentials, network paths, and failure states. Deterministic text snippets already fit HushKey's purpose; keep them distinct from commands that click, send, or run code.

## Preserve local privacy and keep source licenses explicit

The reviewed repositories identify FreeFlow, OpenWhispr, OpenTypeless, SpeakType, Handy, and Blurt as MIT-licensed; HushKey also declares MIT. That makes their code legally more permissive than GPLv3 alternatives, but does not make another app's code or assets necessary: implementing the workflow pattern in HushKey's own SwiftUI/services avoids architectural coupling and keeps its own design. If HushKey directly copies or adapts substantial MIT code, preserve the specific copyright and license notices and record the source; separately audit bundled libraries, speech runtimes, and model weights. FreeFlow's MIT notice names its copyright holder, and the repositories provide the applicable license files ([FreeFlow license](https://raw.githubusercontent.com/zachlatta/freeflow/main/LICENSE), [OpenWhispr license](https://github.com/OpenWhispr/openwhispr/blob/main/LICENSE), [OpenTypeless license](https://github.com/tover0314-w/opentypeless/blob/main/LICENSE), [SpeakType license](https://github.com/karansinghgit/speaktype/blob/main/LICENSE), [HushKey license](../LICENSE)). This is a product-level review, not a complete dependency or legal audit.

“Local transcription” does not guarantee that later cleanup is local. FreeFlow documents no first-party server but its configured transcription/LLM providers receive requests; its optional context service can send app metadata, selected text, and an active-window screenshot. OpenTypeless documents BYOK requests to providers and an optional managed proxy; OpenWhispr offers local and cloud routes; AssemblyAI's Blurt is provider-backed. HushKey should keep local processing as the default and disclose each separate data path before enabling it. Screen capture, selected text, microphone access, Accessibility insertion, meeting audio, and cloud processing need distinct, revocable controls. Do not infer HushKey's privacy from a competitor's marketing claims ([FreeFlow README](https://github.com/zachlatta/freeflow/blob/main/README.md), [FreeFlow context service](https://raw.githubusercontent.com/zachlatta/freeflow/main/Sources/AppContextService.swift), [OpenTypeless README](https://github.com/tover0314-w/opentypeless), [Blurt](https://github.com/AssemblyAI/blurt)).

## Stage delivery around evidence, not feature count

**Stage 1 — prove the core on the target Mac.** Follow the existing [acceptance protocol](TESTING_PROTOCOL.md): grant or refuse permissions deliberately; test voice and whisper, hold/toggle shortcuts, stop/cancel/error cleanup, transcript editing and history, insertion/undo in TextEdit and a second app, and copy recovery. Record each result and fix failures before feature expansion. Do not claim these paths passed from a build or unit test alone.

**Stage 2 — make every capture state recoverable.** Continue improving the status capsule and resilient draft lifecycle, with tests for mic release, focus change, stale target, paste retry, and duplicate prevention. Ensure errors include a specific next action. Keep audio transient unless the user explicitly chooses otherwise.

**Stage 3 — finish selected-text acceptance, then extend profile portability.** The preview-first voice edit is implemented: it uses the selected text and spoken instruction, snapshots and rechecks focus and selection, and requires Apply. Local app profiles now support writing mode, vocabulary, on-device language, snippets, corrections, filler cleanup and a saved Transform style. Profile overrides apply only in Automatic mode; explicit modes retain global preferences. Complete live acceptance first, then include profiles in personal-data backup and add dictionary/snippet/correction import/export. Defer screenshot context and any remote processing behind separate opt-ins.

**Stage 4 — refine existing local models.** Instrument the model setup experience, then benchmark the existing Apple Speech and WhisperKit choices on the M1 Pro using consented samples and session-separated examples. Publish no quality or speed claim until the same corpus, language, and conditions have been compared; retain Apple Speech as the no-download path.

**Stage 5 — decide if specialist workflows earn their cost.** After file and meeting acceptance, evaluate translation and local speaker labels separately with explicit consent and quality checks. Add optional aggregate insights only if users can understand the formula and delete the data. Keep Silent Lab experimental and evidence-gated; it should remain separate from the dependable voice-dictation promise.

## Conclusion

The comparison changes HushKey's next move from “add everything competitors list” to “make the current breadth trustworthy, then extend personalization.” The selected-text editing gap is now implemented, with live acceptance still outstanding. The durable advantage is a Mac-native workflow that makes local processing, target safety, transcript recovery, and silent-input uncertainty visible in the product itself. HushKey can match useful workflows without copying proprietary presentation or turning into a cloud service; the proof will be repeatable acceptance on the target Mac, not a longer feature table.

## Implementation update

After this comparison, HushKey added up to 12 user-defined writing styles in **Transforms**. They support user-authored tone, formatting, and translation instructions, stay in local preferences, and run through Apple's on-device Foundation Model only. Each result is editable and review-first; applying it preserves the existing transcript undo path. The style editor validates names and instruction length, prevents duplicate names, confirms deletion, and persists edits across launches. HushKey has since implemented a dedicated hold shortcut for preview-first voice editing of selected text: it captures only a supported non-secure selection, keeps the spoken instruction out of dictation history, previews locally, and rechecks the original app, field, contents, and selection before Apply. Secure and stale targets fail closed. Unit coverage verifies UTF-16 selection boundaries and prompt separation; live acceptance in TextEdit and a second app is still pending along with microphone, file-model, and meeting-source checks.

Following the supplied FreeFlow/OpenTypeless feature patterns, HushKey now supports editable local app profiles. When dictation is set to **Automatic** and started from another app, a matching profile can select Natural, Message, Email, or Code formatting and override the on-device language, vocabulary, snippets, corrections, filler cleanup, and Transform writing style. Explicit modes keep global preferences. Matching uses only the frontmost app's bundle identifier; app text remains unread unless the separate nearby-context option is enabled. Profile matching, fallback behavior, override resolution, validation, legacy decoding, and version-3 backup portability are unit-tested. Live dictation and insertion acceptance is still required.
